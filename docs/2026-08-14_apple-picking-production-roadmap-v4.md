# Three.js 双人躲避取苹果游戏：V4 制作路线图

> 记录时间：2026-08-14
> 前置文档：`2026-08-14_apple-picking-planning-review-v3.md`
> 状态：核心规则与创意约束已冻结，可进入灰盒 MVP

## 1. 本轮确认

以下规则不再作为待定项：

- `guard` 普通移动接触 `kid` 也可以抓捕。
- 飞扑不是特殊抓捕，而是以随后的停留/恢复为代价，换取一次短暂的快速接近。
- 抓捕和最后一次主动投递发生在同一固定模拟步时，抓捕优先。
- 首版本采用同一把键盘；架构保留手柄输入，后续再启用。
- `kid` 必须主动按键捡苹果，不能接触后自动拾取。
- 首版本不设时间上限或平局；HUD 计时只记录本局已用时间。

## 2. 首版本键位与主动拾取

| 角色 | 移动 | 动作一 | 动作二 |
| --- | --- | --- | --- |
| `guard1` | `W A S D` | `Q` 飞扑 | - |
| `guard2` | `I J K L` | `P` 飞扑 | - |
| `kid` | 方向键 | `Right Ctrl` 捡苹果 | `Right Shift` 丢苹果；在交付区内主动送达 |

以上是灰盒阶段的默认键位，不是最终不可修改的键位。第一次同机试玩必须专门检查键盘多键无冲突能力和两名玩家的手部空间；如果常见键盘无法稳定识别组合输入，应调整默认键位，而不是修改玩法规则。

主动拾取规则：

- 按下一次拾取键，只尝试拾取一个苹果。
- 只检查 `kid` 拾取半径内处于 `Ground` 状态的苹果。
- 同时存在多个苹果时选择最近的一个；距离相同时用稳定实体 ID 决定，保证结果可复现。
- 无敌期间拾取请求无效。
- 找到有效目标后，`kid` 进入短暂的 `Picking` 状态；灰盒初值为 `400ms`（`24 ticks`）。
- `Picking` 期间 `kid` 停止移动但仍可被抓，完成后目标苹果才从 `Ground` 转为 `Carried`。
- 若 `kid` 在停留期间被抓，拾取取消，目标苹果保持 `Ground`。
- 按住按键不能连续拾取；必须释放后再次按下。
- 可拾取苹果应显示轮廓、地面光圈或轻微弹跳，成功和失败需要不同反馈。
- `kid` 进入或停留在交付区都不会自动送达；必须在区内主动按 `Right Shift`，每次送达一个携带苹果。
- 丢苹果和区内送达都是即时动作，不进入 `Picking` 或其他停留状态；每次按下沿处理一个，可通过快速重复按键连续执行。

## 3. 正确的开发策略

建议采用“创意约束 -> 灰盒 MVP -> 玩法验证 -> 垂直切片 -> 内容与品质 -> 联机”的顺序。

MVP 不等于不做设计。MVP 前仍然需要确定游戏承诺、目标情绪、镜头、场地结构和角色轮廓，但不应在玩法尚未证明时投入正式模型、复杂动画、大量场景资产或完整世界观。

## 4. 阶段 0：创意与体验约束

目标是用一页内容回答“这是什么游戏，玩家为什么会觉得有趣”。本阶段不制作正式资产。

需要确定：

| 设计项 | 需要回答的问题 | 当前状态 |
| --- | --- | --- |
| 玩家承诺 | 玩家 A 双线协作围捕偷苹果的孩子，玩家 B 在贪心取舍中偷取并送走苹果 | 已确认 |
| 目标情绪 | 接近欢乐闹剧，主动快乐、轻娱乐 | 已确认 |
| 世界设定 | guard 是苹果园守卫，目标是抓住入园偷苹果的 kid；交付点是带圆形标记和轻微漏斗造型的地点 | 已确认 |
| 角色轮廓 | 守卫共享阵营语言但彼此可分，kid 与守卫在体型、颜色和动作上明显不同 | 约束已确认，造型待设计 |
| 视觉语言 | 苹果、可拾取范围、飞扑、恢复、眩晕、无敌和交付区都必须靠世界内反馈读懂 | 方案待灰盒验证 |
| 镜头 | 单屏固定全场，还是根据三名角色轻微缩放 | 建议固定全场起步 |
| 声音方向 | 明快、滑稽、节奏清楚的欢乐闹剧 | 已确认 |

本阶段只需要概念草图、色板、角色剪影和竞技场平面图，不需要成品 3D 模型。

## 5. 阶段 1：灰盒 MVP

目标是证明完整比赛循环成立，而不是证明画面漂亮。

### MVP 必须包含

- 单个灰盒竞技场、两个 guard、一个 kid、六个苹果和一个圆形目标区。
- 三个角色的完整键盘输入。
- 带短暂停留风险的主动拾取、无停留的快速单个丢弃、携带减速和区内逐个主动投递。
- 普通接触抓捕、三次抓捕获胜。
- 飞扑、恢复、双 guard 飞扑相撞眩晕。
- 抓捕后的全部掉落、无敌、加速和禁止拾取。
- 最小 HUD：已投递苹果、抓捕次数、飞扑恢复状态和比赛结果。
- 开局倒计时、结束冻结和快速重新开始。
- 固定 `60Hz` 模拟、自定义 XZ 平面圆形碰撞和飞扑扫掠检测。

### MVP 明确不包含

- 网络联机。
- 正式角色模型、复杂骨骼动画和电影化演出。
- 多地图、角色选择、成长系统和皮肤。
- 完整设置菜单、按键重绑定界面和移动端触控。
- 高级后处理、复杂物理和破坏系统。

### MVP 通过标准

- 玩家 A 能利用两个 guard 形成包夹，而不是只靠同时冲向 `kid`。
- 飞扑既有追击价值，也有可被 `kid` 利用的恢复窗口。
- 玩家 B 会真实考虑“继续多拿一个”还是“现在投递”。
- 主动拾取的停留时长能给 guard 制造机会，但不会因目标、进度或取消反馈不清而显得失灵。
- 丢一个苹果能成为主动逃生决策，而不是无意义操作。
- 目标区不能被两个 guard 永久无解地封锁。
- 一局能在约 `2~5` 分钟结束，没有长时间僵局。
- 同键盘输入在目标设备上可靠，不出现关键组合丢键。
- 比赛结束后能在约 `3s` 内重新开始。

任何一项没有成立，都先调整规则、数值或竞技场，而不是进入正式美术制作。

## 6. 阶段 2：玩法验证与平衡

建议先进行少量同机对局，记录而不是凭印象修改。

需要观察：

| 问题 | 可调整参数 |
| --- | --- |
| 玩家 A 同时控制两个 guard 是否过载 | 基础速度、转向、飞扑锁向、恢复时间 |
| 普通接触抓捕是否让飞扑失去意义 | guard 与 kid 速度差、障碍布局、飞扑距离 |
| 携带苹果的减速是否产生有趣选择 | 每个苹果减速、最低速度、苹果总数 |
| 拾取停留是否形成风险但不过度惩罚 | 拾取停留时间、拾取半径、进度提示、取消反馈 |
| 丢苹果是否有实际逃生价值 | 掉落位置、拾取锁、单次速度恢复幅度 |
| 终点是否容易被守死 | 终点位置、入口数量、附近掩体和安全距离 |
| 双飞扑眩晕是否可被理解和利用 | 接触窗口、眩晕时长、碰撞反馈 |
| 抓捕后的无敌是否足以脱离包夹 | 无敌时间、加速倍率、guard 碰撞阻挡 |

初始平衡目标不是追求精确胜率，而是双方都能解释自己的失败，并能在下一局改变策略。完成一轮稳定试玩后，再以接近 `40%~60%` 的双方胜率作为粗略健康区间。

## 7. 阶段 3：垂直切片

玩法通过后，制作一个“接近最终质量但内容很少”的完整关卡。这时再集中解决视觉设计、角色设定和场景设定。

### 角色设计

- `kid` 是进入苹果园偷苹果的孩子；动机不需要复杂叙事，以“得手后逃脱”的闹剧感为主。
- 两个 guard 是苹果园守卫；他们的玩法目标只有抓住 `kid`，不是搬运、夺回或保管苹果。
- 两个 guard 应共享阵营语言，但通过体型、颜色、装饰或动作区分。
- 优先保证俯视轮廓和动作状态可读，再增加面部和服装细节。
- 至少需要待机、移动、飞扑、起身、眩晕、抓捕反馈、拾取、携带和丢弃的表现方案。

### 场景设计

- 场景明确为苹果园；边界和障碍服务于围捕、绕行与逃脱，不需要扩展成复杂世界观。
- 交付区是地面上的圆形标记，可配合浅而宽的漏斗造型，但不设置篮子、仓库入口等具体物品。
- 漏斗造型只提供识别和聚焦，不改变首版 XZ 平面移动、碰撞或投递判定。
- 场景布局必须创造绕行、包夹、逃脱和终点争夺，而不是只负责装饰。
- 使用地标、地面颜色和光照引导玩家识别苹果分布与目标区。
- 先完成一张有明确视觉主题的地图，不急于制作第二张。

### 视觉与反馈

- 为三个角色建立互不混淆的主色和轮廓。
- 苹果始终是高显著性目标，不能被环境红色或杂物吞没。
- 飞扑方向、恢复期、眩晕、kid 无敌和携带数量都必须从世界画面中读出，HUD 只做补充。
- 增加动作动画、粒子、音效、镜头冲击和胜负界面，但避免影响多人同屏信息读取。

### UI 与音频

- HUD 显示苹果进度、抓捕进度和两个 guard 的飞扑状态。
- 提供开局控制提示、暂停、重新开始、胜负画面和基础音量设置。
- 音效至少覆盖拾取、丢弃、投递、抓捕、飞扑、撞晕、无敌开始/结束和胜负。

## 8. 阶段 4：内容、品质与兼容

- 根据第一张地图验证出的空间规则制作额外竞技场。
- 加入手柄映射、按键重绑定和无障碍选项。
- 优化动画、材质、灯光、阴影、特效和加载体验。
- 建立性能预算，检查桌面端与目标浏览器。
- 加入确定性测试入口、状态诊断和关键玩法回归测试。
- 完成生产构建、浏览器验证和发布流程。

## 9. 阶段 5：网络联机

网络联机应在本地规则与状态模型稳定后开始，否则每次玩法调整都会同时重做同步协议。

首版提前保留但不实现：

- 设备无关的 `PlayerCommand`。
- 独立于 Three.js 的 `GameSimulation.step()`。
- 固定 tick、稳定实体 ID、可序列化快照和带种子的随机数。
- 规则事件与渲染表现分离。
- 明确的角色所有权：玩家 A 拥有两个 guard，玩家 B 拥有 kid。

联网阶段再实现：

- 房间、加入、准备和重连。
- 服务端权威模拟。
- 客户端输入发送、快照插值和必要的预测/校正。
- 延迟条件下的抓捕、投递和 `150ms` 飞扑窗口裁决。
- 作弊边界、断线胜负和版本兼容。

## 10. 已冻结的视觉设定与规则影响

### 10.1 身份与目标

- `guard1` 和 `guard2` 是负责看守苹果园的守卫，`kid` 是进入果园偷苹果的孩子。
- guard 的唯一比赛目标是抓住 `kid` 三次；苹果不是 guard 的目标，也不是 guard 的可交互物。
- guard 与地面苹果重叠时不会拾取、推走、销毁、归还或计分。guard 对苹果的影响只能来自成功抓捕后触发的 `kid` 全部掉落规则。
- 因此双方不是“争夺苹果”：玩家 A 进行协作围捕，玩家 B 执行偷取、负重取舍与送达。

### 10.2 情绪与表现

- 整体基调冻结为接近欢乐闹剧的主动快乐、轻娱乐，不采用恐怖、阴森或强暴力表达。
- 紧张感来自即时追逐、双 guard 配合和 `kid` 的贪心选择；抓捕、撞晕和掉果用夸张动作、清脆音效与短促特效表现。
- 视觉和声音首先保证规则可读，其次再追求笑料；不能用过强镜头抖动或粒子遮挡多人同屏信息。

### 10.3 交付地点

- 苹果最终送到一处地面圆形标记区；该地点不对应篮子、仓库或其他具体物品。
- 标记区可使用浅而宽的漏斗形地面造型帮助聚焦视线，但灰盒和首版模拟仍将它视为不阻挡移动的圆形传感区。
- 只有 `kid` 携带苹果站在该区域内并主动按下 `Right Shift` 才会交付一个；地面苹果、guard、进入或单纯穿过该区域都不触发苹果状态变化。
- 代码和文案统一称为“交付区”，状态名建议从 `Banked` 改为语义更直接的 `Delivered`。

仓库名已改为 `apple-picking`，文档文件名和前置引用同步采用该名称。

# Three.js 双人躲避取苹果游戏：方案检视与 V3 建议

> 记录时间：2026-08-14
> 检视对象：`2026-08-14_174047_apple-picking-planning-v2.md`
> 状态：待确认关键裁决后冻结

## 1. 检视结论

V2 已经确定了不共享方向键、抓捕后的无敌与加速、圆形终点以及“先同机、后联机”的路线，但还缺少若干会直接影响实现和胜负的边界规则。首个可玩版本开始编码前，建议冻结本文件中的默认裁决。

最重要的缺口如下：

1. V2 漏掉了“每次丢一个苹果并立刻恢复对应速度”的主动动作。
2. 没有明确普通接触是否能抓捕，还是只有飞扑接触才能抓捕。
3. “双飞扑眩晕”没有明确是两个 guard 互相相撞，还是同时碰到 kid。
4. 没有定义飞扑恢复期和眩晕期是否仍能抓捕。
5. 没有定义最后一个苹果投递与第三次抓捕同一模拟帧发生时的胜负优先级。
6. `kid` 键位、丢苹果键和同键盘多键冲突风险尚未确定。
7. “同机”与“local split”表述冲突；本玩法更适合单屏共享镜头，而不是分屏。
8. 只提出 `InputRouter` 还不足以支撑后续网络联机，游戏规则必须与 Three.js 场景对象解耦。

## 2. 建议冻结的完整规则

### 2.1 玩家与镜头

- 两名真人玩家同机对战。
- 玩家 A 同时控制 `guard1` 和 `guard2`；两个 guard 的方向输入完全独立。
- 玩家 B 控制 `kid`。
- 第一版采用单屏共享镜头，镜头展示完整竞技场，不做分屏。
- 开局倒计时结束后才接受移动、飞扑、拾取和抓捕输入。

### 2.2 建议键位

| 角色 | 移动 | 动作 |
| --- | --- | --- |
| `guard1` | `W A S D` | `Q` 飞扑 |
| `guard2` | `I J K L` | `P` 飞扑 |
| `kid` | 方向键 | `Right Shift` 丢一个苹果 |

- 输入层必须读取“按下、持续、释放”三种状态，并在窗口失焦时清空，避免卡键。
- 方向移动支持归一化，斜向移动不能比直线更快。
- 浏览器和普通键盘可能出现多键无冲突能力不足。首版应保留可改键配置，并把玩家 B 使用手柄作为兼容路径，但键盘仍是 MVP 的基础输入。

### 2.3 苹果状态与速度

- 每个苹果只能处于 `Ground`、`Carried` 或 `Banked` 三种状态之一。
- `kid` 接触地面苹果时自动拾取；无敌期内拾取无效。
- 携带速度建议使用明确公式：

```text
kidSpeed = baseSpeed * max(minCarryMultiplier, 1 - carryCount * slowdownPerApple)
```

- 建议初值：`slowdownPerApple = 0.10`，`minCarryMultiplier = 0.55`。
- 按一次丢弃键只丢一个苹果，优先丢弃最后拾取的苹果。
- 苹果落在 `kid` 身后一个角色直径外，并获得约 `0.6s` 的拾取锁，防止原地立即捡回。
- 丢弃成功的同一模拟帧立刻减少 `carryCount` 并重算速度；不设置动作冷却，但必须以一次按下沿只触发一次，不能按住连续丢弃。

### 2.4 抓捕、无敌与掉落

- `guard` 在 `Move` 或 `Pounce` 状态接触 `kid` 均可触发抓捕；飞扑的价值是快速拉近距离，而不是唯一抓捕手段。
- `guard` 在 `Recover` 或 `Stunned` 状态不能抓捕，避免倒地角色成为被动陷阱。
- 一次有效抓捕按以下固定顺序结算：
  1. 抓捕次数加一。
  2. `kid` 携带的全部苹果变为 `Ground`，散落在其周围。
  3. `kid` 进入无敌状态，不回到重生点。
  4. 无敌期间 `kid` 不能被再次抓捕，也不能拾取苹果。
  5. 因苹果已全部掉落，速度先恢复到基础值，再乘无敌加速倍率。
- 建议初值：无敌 `1.2s`，速度倍率 `1.25x`，掉落苹果拾取锁与无敌同时结束。
- 无敌状态必须有清晰的角色闪烁、轮廓或颜色提示，并在 HUD 显示剩余抓捕次数。

### 2.5 飞扑与双 guard 眩晕

- 每个 guard 的状态为 `Move -> Pounce -> Recover -> Move`，眩晕会强制进入 `Stunned -> Move`。
- 飞扑开始时锁定方向；飞扑期间不能转向。
- `Pounce` 使用高速位移，结束后进入不能移动、不能抓捕的 `Recover`。
- “双飞扑眩晕”明确为：两个 guard 都处于 `Pounce`，且彼此的碰撞体发生接触；两次飞扑启动时间差不超过 `150ms` 时，双方同时进入 `Stunned`。
- 两个 guard 同时接触 `kid` 不触发自身眩晕；对 `kid` 只结算一次抓捕。
- 建议初值：飞扑 `220ms`，恢复 `700ms`，眩晕 `1000ms`，冷却从恢复或眩晕结束后开始计算。
- 飞扑需使用扫掠圆或分段检测，不能只检查帧末位置，否则低帧率时会穿过角色。

### 2.6 圆形目标区与胜负

- 圆形目标区是传感区域，不阻挡角色移动。
- `kid` 携带苹果进入目标区时，将当前携带的全部苹果原子化转为 `Banked`；已入库苹果从场地移除，不能被抢回。
- 地面苹果滚入或被丢进目标区不自动入库，避免无意碰撞决定胜负；必须由 `kid` 携带进入。
- 每个固定模拟步按以下顺序处理关键事件：输入、移动、碰撞、抓捕、苹果投递、胜负检查。
- 因抓捕先于投递，如果最后一个苹果投递与第三次抓捕同一模拟步发生，则先掉落苹果并判玩家 A 获胜。这个优先级必须写进测试和联机协议。
- `bankedCount == totalAppleCount` 时玩家 B 获胜；`catchCount >= 3` 时玩家 A 获胜。游戏结束后立即冻结玩法输入，只保留重新开始。

## 3. 首个竞技场建议

- 采用固定大小的矩形竞技场和俯视/斜俯视固定镜头。
- `kid`、两个 guard 和圆形目标区分别从不同区域开始，避免开局立即包夹或守门。
- 建议先放置 `6` 个苹果。苹果分布应迫使 `kid` 决定“多拿后冒险投递”或“少量多次保持速度”。
- 灰盒阶段放置少量大型障碍，形成至少两条可绕行路线；纯空场会让双 guard 包夹成为唯一策略。
- 目标区附近不能形成只有一个入口的死角，否则玩家 A 可以永久封锁终点。
- 第一局前 `10~15s` 应出现第一次“继续搜集还是先投递”的真实决策。

## 4. 技术实现边界

### 4.1 碰撞方案

- 首版推荐自定义二维圆形碰撞，而不是 Rapier：角色、苹果和目标区都可投影到 XZ 平面，用圆形重叠与扫掠检测即可完成规则。
- Three.js 只负责表现；碰撞体使用独立的半径和位置数据，不能直接用模型网格做碰撞。
- 模拟使用固定 `60Hz` 步长，并限制累计帧时间，避免飞扑窗口和无敌计时随帧率变化。

### 4.2 为联机保留的结构

- `InputRouter` 只把键盘或手柄转换成与设备无关的 `PlayerCommand`，不直接移动 Three.js 对象。
- `GameSimulation.step(tick, commands)` 独立维护角色、苹果、计时器、碰撞和胜负，并产生领域事件。
- `GameRenderer` 根据模拟快照更新模型、动画、特效和 HUD，不拥有规则状态。
- 所有实体使用稳定 ID；时间窗口使用模拟 tick，而不是 `Date.now()`。
- 游戏状态可序列化为快照；随机出生或散落位置使用带种子的随机数。
- 后续联机优先采用服务端权威模拟、客户端发送输入、快照插值/校正。首版不必实现网络，也不必为了网络强求跨平台浮点锁步确定性。

建议的更新顺序为：

```text
采集输入 -> 生成命令 -> 固定步长模拟 -> 产生事件 -> 更新动画/VFX/HUD -> 渲染
```

## 5. 开始编码前仍需确认的三项产品决定

1. 是否接受“普通移动接触也能抓捕”；如果只允许飞扑抓捕，整体平衡和 guard 基础速度需要重新设计。
2. 是否接受“抓捕优先于同帧投递”；另一种选择是目标区内优先投递，或允许平局。
3. 玩家 B 是否必须只用同一把键盘；若允许手柄，实际试玩的多键冲突和两人手部空间会明显改善。

确认这三项后，规则才适合冻结并进入灰盒实现。

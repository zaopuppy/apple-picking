# Three.js 双人躲避取苹果游戏：V5 落地规格与方案检视

> 记录时间：2026-08-14
> 前置文档：`2026-08-14_apple-picking-production-roadmap-v4.md`
> 状态：创意约束已冻结，灰盒 MVP 可进入实现

## 1. 本轮裁决

### 1.1 非对称目标

- 玩家 A 控制两名苹果园守卫，唯一目标是在一局内抓住 `kid` 三次。
- 玩家 B 控制进入果园偷苹果的 `kid`，目标是拾取并把全部苹果送进交付区。
- guard 不拾取、不搬运、不归还、不销毁苹果，也不因接触苹果获得分数或状态变化。
- guard 可以根据苹果和交付区的位置预判 `kid` 的路线，但这是围捕策略，不是守护或争夺苹果的第二套目标。
- 首版比赛没有时间上限或平局；HUD 只正向记录已用时间，直到一方达成胜利条件。

### 1.2 体验基调

- 目标情绪是欢乐闹剧、主动快乐和轻娱乐。
- 紧张来自追逐和临场决策，不来自恐怖、伤害或惩罚感。
- 飞扑落空、两个 guard 相撞、抓捕后苹果散落是主要喜剧节拍；反馈应短促、夸张、清楚，不遮挡场面。

### 1.3 交付区

- 交付区是一处地面圆形标记，没有篮子、仓库入口或其他具体物品。
- 视觉上可做成浅而宽的漏斗形地面，但漏斗不产生坡度加速、吸附、滑落或额外碰撞。
- 规则上它只是圆形传感器：`kid` 携带苹果站在区内并主动按 `Right Shift` 时，每个按下沿将一个携带苹果转为 `Delivered`。
- `kid` 进入或停留在交付区不会自动送达；地面苹果和 guard 进入也不会触发任何规则。

## 2. 游戏设计简报

| 项目 | 冻结内容 |
| --- | --- |
| 玩家承诺 | 一名玩家分心操控双守卫协作围捕，另一名玩家在偷得更多与及时逃脱之间反复冒险 |
| 目标感觉 | 明快、滑稽、易上手，每局都有可复述的追逐笑点 |
| 玩家 A 主动词 | 移动、包夹、预判、飞扑 |
| 玩家 B 主动词 | 移动、停留拾取、携带、快速丢弃、送达 |
| 压力 | 拾取暴露窗口、双向围捕、携带减速、飞扑突进、交付路线可预测 |
| 奖励 | 玩家 A 累积抓捕次数；玩家 B 永久增加已送达苹果数 |
| 失败与重试 | `kid` 被抓三次或全部苹果送达后结束；冻结输入并约 3 秒内允许重开 |
| 技能表达 | A 的双线站位、夹角与飞扑时机；B 的路线、负重规模、丢果和诱骗飞扑时机 |
| 可读性承诺 | 玩家无需阅读说明即可看出谁在追谁、谁能拾果、谁处于恢复/眩晕/无敌以及交付进度 |
| 非目标 | 网络、多地图、成长系统、正式模型、复杂物理、guard 苹果交互 |

## 3. 双方核心循环契约

### 玩家 A：守卫

```text
玩家用双 guard 的移动、站位和飞扑围住 kid；分心控制、飞扑恢复和互撞眩晕制造风险；
有效接触获得一次抓捕进度，累计三次获胜；若让 kid 送完全部苹果则失败并快速重开。
```

### 玩家 B：kid

```text
玩家主动停留拾取苹果并决定继续负重、快速丢果提速或前往交付区逐个主动送达；拾取暴露窗口、双 guard 围捕和携带减速制造风险；
成功交付永久推进苹果进度，被抓则掉落全部携带物并累计失败，三次被抓后重开。
```

该设计的关键不是双方争同一种资源，而是“路线可预测的收集者”对“需要分心协作的围捕者”。

## 4. 灰盒竞技场方案

### 4.1 第一版空间参数

以下数值是首轮试玩起点，不是最终平衡结论：

| 参数 | 初值 | 目的 |
| --- | ---: | --- |
| 竞技场 | `24m x 18m` | 固定镜头能展示全场，同时留出双线包夹空间 |
| 交付区传感半径 | `2.0m` | 允许多方向进入，不形成像素级判定 |
| 漏斗视觉外径 | `5.0m` | 在俯视视角下清楚识别交付地点 |
| 漏斗视觉落差 | `0.15m` | 只形成轻微造型，不暗示真实滑动物理 |
| 苹果数量 | `6` | 支持多拿冒险与少量多次两种路线 |
| 大型障碍组 | `3` 组 | 形成绕行、切线和视线地标，避免纯空场追逐 |
| 主要通路净宽 | `3.0m` 以上 | 允许错身和飞扑，不形成单人硬堵 |

### 4.2 布局约束

- 交付区放在偏离中心但不贴墙的位置，至少保留三个可接近方向；不得放进单入口凹角。
- 六个苹果分成近、中、远三个风险层，不能排成一条无需选择的最优路线。
- `kid`、两个 guard 和交付区分别起始于不同区域，开局倒计时结束后不能立刻发生抓捕。
- 障碍必须创造绕行与夹击选择，但不遮住角色、苹果或交付区的俯视轮廓。
- 第一局前 `10~15s` 内应出现“再拿一个还是先送达”的第一次真实决策。
- guard 在交付区附近等待属于合法围捕策略，但地图必须让 `kid` 有诱骗飞扑、换向和多入口接近的反制空间。

## 5. 权威规则与初始调参

### 5.1 状态模型

```text
MatchState: Countdown | Playing | KidWin | GuardWin
GuardState: Move | Pounce | Recover | Stunned
KidState: Normal | Picking | Invincible
AppleState: Ground | Carried | Delivered
```

- `Delivered` 苹果从玩法场地移除，不能被抢回。
- `Ground` 苹果静止在 XZ 平面；掉落时直接生成稳定散落位置，不引入刚体滚动。
- guard 的碰撞查询不包含苹果；苹果规则只读取 `kid`、拾取/丢弃输入、掉落锁和交付区。
- 拾取按下沿找到目标时，`kid` 进入 `Picking` 并记录稳定的目标苹果 ID；停留结束前苹果仍是 `Ground`。
- `Picking` 期间 `kid` 不能移动但仍可被抓；被抓会取消拾取，目标苹果保持 `Ground`。
- 丢弃不对应 Kid 状态，也不产生停留、恢复或冷却；每个按下沿立即丢一个并重算速度，快速重复按键可连续丢弃。
- `Picking` 期间仍允许即时丢弃已经携带的苹果，且不会重置拾取计时。
- `Right Shift` 在交付区外表示即时丢弃，在交付区内表示主动送达；区内每个按下沿只送达一个，快速重复按键可连续送达。

### 5.2 初始调参表

| 参数 | 初值 |
| --- | ---: |
| 固定模拟频率 | `60Hz` |
| 抓捕获胜次数 | `3` |
| `kid` 基础速度 | `4.8m/s` |
| guard 基础速度 | `4.2m/s` |
| 每个苹果减速 | `10%` |
| 最低携带速度倍率 | `55%` |
| 主动拾取停留 | `400ms`，即 `24 ticks` |
| guard 飞扑持续 | `220ms` |
| guard 飞扑速度 | `9.0m/s` |
| 飞扑恢复 | `700ms` |
| 飞扑恢复后冷却 | `600ms`，即 `36 ticks` |
| 双飞扑启动窗口 | `150ms`，即 `9 ticks` |
| 双 guard 眩晕 | `1000ms` |
| `kid` 抓捕后无敌 | `1200ms` |
| 无敌速度倍率 | `1.25x` |
| 抓捕掉果拾取锁 | `1200ms` |
| 主动丢果拾取锁 | `600ms` |

首轮调参优先级：先保证普通 guard 追不上空手直线奔跑的 `kid`，再用双线站位和飞扑补足围捕能力；否则普通接触抓捕会压过所有其他策略。

### 5.3 固定步结算顺序

```text
读取本 tick 命令
-> 区外立即结算丢弃；区内记录一次主动交付请求；尝试开始 Picking
-> 计算移动与飞扑扫掠（Picking 时 kid 位移为零）
-> 解决角色和场地碰撞
-> 结算 guard 互撞眩晕
-> 结算抓捕并取消被抓 kid 的 Picking
-> 推进并尝试完成未取消的 Picking
-> 未被抓时结算一次主动交付
-> 检查胜负
-> 产生领域事件
```

- 第三次抓捕与最后交付同 tick 时，抓捕先结算，玩家 A 获胜。
- 同一 tick 两个 guard 都接触 `kid` 时只增加一次抓捕。
- `Recover`、`Stunned` guard 不能抓捕；`Invincible` kid 不能被抓也不能拾取。
- `Picking` 完成与有效抓捕发生在同一 tick 时，抓捕优先并取消拾取。
- 游戏结束后清空持续输入，只保留重新开始命令。

## 6. 建议代码边界

```text
src/
  core/       GameLoop, InputRouter, seededRng, diagnostics
  game/       GameSimulation, GameState, commands, events, config
  entities/   guard, kid, apple, deliveryZone
  systems/    movement, collision, pounce, capture, apple, winCondition
  render/     scene, camera, entityViews, feedback, orchardGreybox
  ui/         HUD, countdown, resultOverlay
  tests/      rule tests, deterministic scenarios, browser smoke tests
```

- `InputRouter` 只产生设备无关的 `PlayerCommand`，不直接修改 Three.js 对象。
- `GameSimulation.step(tick, commands)` 是唯一规则所有者，输出可序列化快照和领域事件。
- `GameRenderer` 只消费快照与事件；浅漏斗地形属于渲染层，交付传感器属于模拟层。
- 所有计时使用 tick，所有实体使用稳定 ID，散落位置使用带种子的随机数。
- 第一版使用自定义 XZ 圆形碰撞；角色模型和漏斗网格不能充当规则碰撞体。

## 7. 实现切片与退出标准

### 切片 1：确定性模拟骨架

- 完成固定步循环、输入命令、状态快照、种子随机和重新开始。
- 退出标准：相同种子与命令序列产生相同最终快照。

### 切片 2：竞技场与三角色移动

- 完成固定全场镜头、边界、三组障碍、三套键位和斜向归一化。
- 退出标准：三名角色可同时移动，失焦后不粘键，不能穿越边界和障碍。

### 切片 3：苹果循环

- 完成带 `400ms` 停留的主动拾取、携带减速、无停留的快速单个丢弃、拾取锁、区内逐个主动交付和进度 HUD。
- 退出标准：guard 接触苹果不会改变状态；`kid` 拾取时停止且可被抓；丢弃立即完成；苹果能完成从 `Ground` 到 `Carried` 再到 `Delivered` 的闭环。

### 切片 4：围捕循环

- 完成普通接触抓捕、飞扑扫掠、恢复、双 guard 互撞眩晕、抓捕掉果、无敌与三次获胜。
- 退出标准：抓捕优先级、单 tick 去重、不可抓捕状态和快速重开全部通过规则测试。

### 切片 5：可读性与闹剧反馈

- 完成倒计时、世界内状态提示、最小 HUD、抓捕/掉果/撞晕反馈和占位音频事件。
- 退出标准：旁观者无需解释即可辨认追捕关系、无敌、恢复、眩晕和交付进度。

### 切片 6：同机试玩门槛

- 完成生产构建、桌面浏览器验证、同键盘冲突测试和至少五局记录。
- 退出标准：一局约 `2~5` 分钟，双方都能说明失败原因，不存在交付区永久封锁或稳定无解策略。

## 8. 必须先写的规则测试

1. guard 与 `Ground` 苹果重叠，苹果状态和位置不变。
2. `kid` 接近苹果但未按拾取键，苹果保持 `Ground`。
3. 同时有多个可拾取苹果时按距离、再按稳定 ID 选择一个。
4. 拾取开始后的前 `23 ticks` 苹果仍是 `Ground`，`kid` 不能移动但可以被抓。
5. 第 `24 ticks` 无抓捕时目标苹果转为 `Carried`；同 tick 被抓则拾取取消。
6. 持有苹果时按一次丢弃立即减少一个 `Carried`，不进入 `Picking`；连续快速按下可逐个丢完。
7. `Picking` 期间丢弃已有苹果不重置拾取计时。
8. `kid` 携带多个苹果进入或停留在交付区但未按键时，苹果仍为 `Carried`。
9. `kid` 在交付区内每按一次 `Right Shift` 只送达一个；快速重复按键可逐个送完且不进入 `Picking`。
10. `Ground` 苹果位于交付区内不会自动送达。
11. `Recover` 或 `Stunned` guard 接触 `kid` 不触发抓捕。
12. 两个可抓捕 guard 同 tick 接触 `kid` 只记一次。
13. 两次飞扑启动相差不超过 `9 ticks` 且 guard 相撞时双方眩晕；仅同时接触 `kid` 不眩晕。
14. 第三次抓捕与最后一次主动交付同 tick 时，玩家 A 获胜且苹果未送达。
15. 模拟经过五分钟仍未满足任一胜利条件时继续比赛，不产生超时或平局。
16. 重开后苹果、计时器、输入、抓捕次数和领域事件队列全部复位。

## 9. 方案检视结论

### 已解决

- 身份、目标和情绪已经一致：守卫围捕偷果者，不再使用“双方争夺苹果”的表述。
- 交付区不依赖具体道具，浅漏斗造型和圆形传感规则已经分层。
- guard 与苹果无规则交互，减少了一套不必要的搬运/归还状态和胜负歧义。
- 双方核心循环、固定步顺序、初始数值、模块边界与测试入口已能直接指导灰盒实现。

### 仍需试玩验证

- 一名玩家同时控制两个 guard 的认知负荷是否过高。
- `4.2m/s` guard 配合飞扑能否形成有效围捕，又不会让普通接触变成无脑优势。
- 三个交付方向是否足以抵抗双 guard 长时间守点。
- 六个苹果与 `10%` 逐个减速能否稳定产生“再拿一个还是先交付”的选择。
- `400ms` 拾取停留是否足以制造围捕机会，又不会让拾取在正常距离下成为必抓陷阱。
- 欢乐反馈是否清楚但不过量，尤其是双 guard 撞晕与大量掉果同时发生时。

这些项目必须通过真实同机对局验证；在验证前不进入正式角色模型、复杂动画或网络联机。

# 桌面网页联机架构与首期实施记录

日期：2026-08-16  
状态：方案已确认；Phase 0、Phase 1 与演示所需房间闭环已实施

## 结论先行

长期方案仍是“服务端权威、客户端预测与插值、邀请房间制”的 2–3 人桌面浏览器游戏。本次先完成正确性优先的 2 人演示竖切：

- 一个 Node.js 进程维护多个短生命周期房间；每个房间拥有唯一的 `GameSimulation`，以现有 60 tick/s 固定步长推进。
- 浏览器只发送自己拥有角色的输入意图，不发送位置、得分、命中或胜负结果；服务端计算全部碰撞、拾取、投递、抓捕和胜负。
- 客户端继续使用现有 Three.js、HUD 和音频表现层，消费服务端快照与事件。本期直接显示权威快照；远端插值和本地预测留在 Phase 2。
- MVP 网络层建议用 Socket.IO，而不是裸 WebSocket、WebRTC 房主制或确定性锁步。它与当前普通 TypeScript 快照/事件模型衔接最小，房间、重连和确认机制也足够完成首版。
- 首版只允许服务端内置地图，不允许房主从 `localStorage` 上传自定义地图。房间固定 `mapId + mapVersion + contentHash + buildVersion`，所有客户端必须与服务端版本一致。
- 本地同键盘模式继续保留，并作为规则回归与网络故障时的可玩入口；在线模式通过新的会话驱动接入，不在 `GameSimulation` 中加入 Socket、DOM 或 Three.js 依赖。
- 这是纯演示项目，本期明确使用 HTTP + WebSocket，不配置 SSL/TLS，也不按公网生产服务承诺安全性与可用性。

这份建议的重点不是“把三个键盘输入广播给其他浏览器”，而是把规则真源移到服务器。否则任意客户端都能声明自己已拾取、没被抓或已经获胜，断线与版本差异也会让三端状态永久分叉。

## 1. 范围与默认假设

### 1.1 首版目标

- 桌面 Chrome 优先，本机双标签或受信任局域网中的浏览器可通过房间码加入。
- 不登录账号即可创建房间、选角色、准备、开始、完成一局和再来一局。
- 延续当前非对称玩法和地图，不在联机首版同时重做规则、镜头或关卡。
- 在常见的 30–120 ms 往返延迟下，移动仍有即时反馈，其他角色运动连续，抓捕和投递结果以服务端为准。
- 短暂掉线可以回到原座位和当前房间，不产生重复音效、重复计分或角色持续移动。

### 1.2 暂不纳入

- 移动端触控、鸿蒙端联机适配。
- 账号、好友、公开匹配、排行榜、赛季与永久存档。
- 语音、文字聊天、观战、录像下载和反作弊运营后台。
- 玩家上传自定义地图、跨版本房间、进行中途换人。
- 跨地域多机房、无缝房间迁移和大规模水平扩容。
- WebRTC P2P、回滚锁步或专用 UDP/WebTransport 通道。
- SSL/TLS 证书、HTTPS/WSS、生产域名与公网安全加固。

## 2. 当前项目为什么适合演进到权威服务器

现有代码已经具备联机改造最重要的边界：

| 现状 | 对联机的价值 | 仍需处理的问题 |
| --- | --- | --- |
| `src/game/GameSimulation.ts` 不依赖 Three.js、DOM、HUD 或音频 | 同一规则可在 Node.js 服务端运行 | 需要验证 Node 与浏览器对同一输入带的重放一致性 |
| `GameSimulation.step(GameCommands)` 每 tick 接受三个角色的命令 | 网络输入可以直接汇合成服务端 tick 命令 | 在线模式必须按座位过滤命令，客户端不能控制未拥有角色 |
| 规则以 60 tick/s 固定步长运行 | 服务端可沿用同一时间尺度，不改所有以 tick 表示的平衡参数 | Node 计时器要用累积器补偿抖动，不能假设 `setInterval(16.6)` 精确触发 |
| `SimulationStep` 已分为 `snapshot` 与 `events` | 快照适合状态同步，事件适合一次性音效/VFX | 网络事件必须增加稳定的 `eventId` 和 `tick`，客户端去重 |
| 随机数可通过 `seed()` 固定 | 便于输入重放、故障复现和房间审计 | RNG 内部状态没有进入当前快照，不能仅凭 `GameSnapshot` 中途续跑 |
| 渲染、HUD、音频只消费状态 | 可继续保留现有表现代码 | `Game` 目前直接拥有本地模拟，需要改为可切换的会话驱动 |
| 地图有版本、解析与可玩性校验 | 服务端可复用地图验证 | `Game` 目前允许从浏览器 `localStorage` 选图，在线房间不能信任它 |
| Playwright 有真实键盘路径和测试钩子 | 可扩展到两个或三个浏览器上下文 | 还没有延迟、断线、重连、重复包和多客户端收敛测试 |

需要特别区分两个概念：

- `GameSnapshot` 是“给画面看的公开状态”，当前没有包含 `previousPosition`、RNG 状态、`dropSerial`、部分动作内部时间点等全部可恢复信息。
- `SimulationCheckpoint` 应是“可完整恢复和重放的规则状态”，需要有独立版本，不能用展示快照反向拼装。

服务端权威本身不要求客户端拥有完整 checkpoint；只有做全模拟预测、服务器进程恢复或录像快进时才需要它。因此建议先把两者概念分开，再按阶段实现。

## 3. 玩家模式：协议支持 2–3 人，首测以 2 人为主

早期设计的核心关系是两个阵营：一名玩家控制 `kid`，另一名玩家同时控制 `guard1` 与 `guard2`。当前键位又天然允许把两名守卫拆给两位玩家。网络协议不应把“一个连接等于一个角色”写死，而应使用座位与角色所有权：

```text
kid seat       -> owns [kid]
guard-team seat（2 人模式） -> owns [guard1, guard2]

或

kid seat       -> owns [kid]
guard-1 seat   -> owns [guard1]
guard-2 seat   -> owns [guard2]
```

推荐产品默认值：

- 首个可玩测试采用 2 个浏览器客户端，忠实保留原始非对称设计和平衡关系。
- 房间配置保留 `guardControlMode: 'shared' | 'split'`，之后可以用 3 人模式做额外试玩。
- 一局开始后锁定座位与所有权；重连只能取回原座位，不能借重连换阵营。

这样既不妨碍快速做出竖切，也不会为了以后支持 3 人重写输入协议。

## 4. 拓扑方案比较

### 4.1 规则真源放在哪里

| 方案 | 优点 | 主要代价 | 本项目判断 |
| --- | --- | --- | --- |
| 服务端权威模拟 | 结果一致、容易限制作弊、房主退出不影响权威、可记录输入重放 | 需要部署后端；本地响应需预测 | **推荐** |
| 房主权威的 WebRTC P2P | 少量实时流量不经过游戏服务器 | 仍需信令，复杂 NAT 下需要 TURN；房主有作弊权且退出会中断或迁移 | 不作为首版 |
| 所有客户端确定性锁步 | 带宽低，现有固定 tick 和种子可复用 | 等待最慢输入；浏览器版本/浮点差异会放大；掉线和作弊处理复杂 | 不适合快速追逐游戏首版 |
| 纯状态中继 | 最快做出演示 | 没有可信规则真源，碰撞和胜负容易分叉 | 只可做一次性原型，不进入产品分支 |

WebRTC 数据通道本身适合点对点数据，但连接建立仍需要额外信令；本项目只有 2–3 人，节省的服务器带宽远小于房主迁移、公平性和排障复杂度。

### 4.2 服务端网络库

| 方案 | 与现有代码的匹配 | 代价 | 结论 |
| --- | --- | --- | --- |
| Socket.IO 4.x | 可以直接发送普通 TypeScript/JSON 消息；房间、确认、自动重连和连接恢复可用；保留自定义 60 Hz 模拟 | 断线期间默认不是完整可靠日志，应用仍要做序号、确认和全量重同步 | **MVP 推荐** |
| Colyseus 0.17 | 内置权威房间、固定模拟间隔、状态 patch、匹配与重连模型 | 若使用 Schema 同步，需要维护另一套状态模型并调整 TS 装饰器配置；与当前 `GameSnapshot` 有重复表达 | 当公开匹配、观战、复杂房间生命周期成为近期需求时复评 |
| 裸 WebSocket | 依赖最少、协议完全可控 | 房间、重连、确认、心跳、会话恢复、消息校验和测试设施都要自行实现 | 当前没有收益 |

选择 Socket.IO 不代表依赖它保证“每个游戏事件绝不丢”。官方文档说明连接内消息保持顺序，但默认到达语义是 at-most-once，成功连接恢复也不能替代失败后的全量同步。因此游戏协议仍要明确哪些消息可以覆盖、哪些必须确认与去重。

### 5.1 代码边界建议

不必在首版建立 monorepo。可以先在同一仓库增加服务器入口，共享纯规则模块：

```text
src/
  game/                    继续作为浏览器与 Node 共用的确定性规则
  net/
    protocol.ts            双端共享的协议类型、版本与运行时校验入口
    OnlineGameDriver.ts    连接、输入发送、快照缓冲、预测与校正
    LocalGameDriver.ts     封装当前本地 GameSimulation 行为
    ClockSync.ts           RTT、服务端 tick 偏移与插值时间
server/
  index.ts                 HTTP、Socket.IO、健康检查与生命周期
  RoomManager.ts           创建/加入/销毁房间与房间码
  AuthoritativeGameRoom.ts 座位、输入队列、60 Hz 累积器、广播与重连
  MapCatalog.ts            服务端允许的地图及内容 hash
tests/
  multiplayer.spec.ts      多浏览器上下文、断线和状态收敛
  protocol.spec.ts         非法、重复、乱序和跨版本消息
```

`Game` 不再直接假设自己总能调用本地 `simulation.step()`，而是依赖一个窄接口，例如：

```ts
interface GameDriver {
  submitLocalCommands(commands: GameCommands): void;
  update(deltaSeconds: number): void;
  getRenderSnapshot(): GameSnapshot;
  drainPresentationEvents(): readonly GameEvent[];
  getConnectionState(): ConnectionState;
  dispose(): void;
}
```

本地驱动继续在当前浏览器循环里推进 60 Hz 模拟；在线驱动不裁决规则，只管理网络时间、快照和预测。Three.js、HUD 与 Audio 不需要知道状态来自本机还是服务器。

### 5.2 服务端房间状态机

```text
Creating -> Lobby -> Countdown -> Playing -> Finished -> RematchLobby
               ^          |          |
               |          v          v
               └──── Reconnecting / Abandoned
```

- `Lobby`：选择座位、校验版本与地图、准备。
- `Countdown`：仅服务端倒计时；客户端本地显示，不可提前移动。
- `Playing`：服务端推进规则并广播。
- `Reconnecting`：有玩家意外断线时暂停模拟并保留座位，建议 15 秒。
- `Finished`：服务端锁定最终状态，玩家分别点击“再来一局”；全部在线玩家准备后重新倒计时。
- `Abandoned`：超时未回，返回房间大厅；首版不自动判对方获胜，避免网络波动污染胜负数据。

在线模式中，当前 `R` 键不应直接进入 `GameCommands.restartPressed`。它可以打开“请求重开/再来一局”，最终仍由房间状态机决定。否则任何客户端都能单方面重置比赛。

## 6. 同步模型与建议参数

以下是首轮实验值，不是永久常量：

| 项目 | 建议起点 | 原因 |
| --- | --- | --- |
| 服务端模拟 | 60 tick/s | 沿用现有所有 tick 制规则与手感 |
| 输入发送 | 30 次/s，变化和动作边沿立即发送 | 移动足够细；避免按渲染帧无条件发包 |
| 权威快照 | 20 次/s | 当前实体很少，全量快照便于正确性与排障 |
| 客户端渲染 | 60 fps 或设备刷新率 | 与网络频率解耦 |
| 远端插值缓冲 | 100 ms 起调 | 覆盖常见抖动，之后以测试数据调整 |
| 无新输入保护 | 250 ms 后强制该角色中立输入 | 防止失焦、睡眠或断线后一直移动 |
| 重连保留 | 15 秒 | 足够覆盖短时网络切换，又不长期占房 |

### 6.1 服务端 tick

服务端应使用单调时钟和固定步长累积器：

1. 读取每个角色最后一个已接受的 held input 和本 tick 待消费的 edge actions。
2. 拼出完整 `GameCommands`。
3. 调用一次 `GameSimulation.step()`。
4. 给本 tick 事件分配 `(matchId, tick, eventIndex)` 组成的稳定 `eventId`。
5. 到达广播间隔时发送全量权威快照；事件随下一条快照或独立事件批发送。
6. 如果进程短暂停顿，限制单轮补 tick 数量并记录 `tickLag`，避免无限追赶拖垮房间。

每个房间串行推进，不让多个异步回调同时修改同一个模拟。一个房间内的输入接收只写队列，规则更新只在 tick 循环消费。

### 6.2 输入消息

建议按连接拥有的角色批量发送：

```ts
type ClientInputFrame = {
  protocolVersion: 1;
  matchId: string;
  seq: number;
  clientTick: number;
  actors: Partial<Record<'guard1' | 'guard2' | 'kid', {
    moveX: number;
    moveZ: number;
    actionPressed: boolean;
    dropPressed: boolean;
  }>>;
};
```

服务端处理规则：

- 检查 `protocolVersion`、`matchId`、消息大小、有限数值和字段白名单。
- 将移动向量重新归一化并限制在 `[-1, 1]`；不要相信客户端已经归一化。
- 删除该连接不拥有的角色命令。
- `seq <= lastAcceptedSeq` 的帧只用于重发确认，不再次触发动作边沿。
- `actionPressed` / `dropPressed` 在服务端最多消费一次；客户端在收到 `lastProcessedInputSeq` 前可携带最近未确认边沿重发。
- 客户端时间不决定碰撞或冷却，只用于诊断；服务端 tick 才是真实时间。

这样即使断线恰好发生在按下拾取或飞扑的瞬间，也不会因盲目重试造成双重动作。

### 6.3 快照与事件消息

```ts
type ServerStateFrame = {
  protocolVersion: 1;
  buildVersion: string;
  matchId: string;
  serverTick: number;
  sentAtMs: number;
  lastProcessedInputSeqByPlayer: Record<string, number>;
  snapshot: GameSnapshot;
  checkpoint?: SimulationCheckpoint; // Phase 2 的预测回放载荷
  events: Array<GameEvent & { eventId: string; tick: number }>;
};
```

- 快照是可覆盖数据：旧快照到达后直接丢弃，短暂漏一帧由下一全量快照修复，不做数据库级补发。
- `checkpoint` 不是 Phase 1 渲染同步的前置条件；只有启用完整客户端预测时才发送，并带自己的格式版本。不能拿 `GameSnapshot` 代替它。
- 一次性事件按 `eventId` 去重；音效/VFX 只在事件第一次越过渲染时间线时触发。
- 房间加入、座位变更、准备、开始、放弃和再来一局属于控制消息，需要 ack、明确错误码和幂等请求 ID。
- 重连恢复失败时，客户端请求一份 `RoomState + 最新全量快照`，清空插值与事件缓冲后重新建立时间线。
- 服务端不得为慢客户端无限排队历史快照；网络层只保留最新可替换状态，传输不可写或客户端持续落后时丢弃中间快照并记录 slow-consumer 指标，必要时断开后走重连全量同步。

### 6.4 插值、预测与校正

分两步交付可以降低首次联机风险：

1. **正确性竖切**：所有角色都渲染权威快照插值，不做预测。它会让本地操作感到约一个 RTT 的延迟，但最容易证明房间、输入和规则没有分叉。
2. **可玩性竖切**：本地拥有的角色立即预测，远端角色继续插值；权威快照到来后，从服务器已处理输入序号重放未确认输入，并在很短时间内平滑视觉误差。

不要在第一步还没收敛时直接做复杂预测。预测需要先选择一种策略：

- 推荐长期方案：为 `GameSimulation` 增加有版本的 `SimulationCheckpoint` 导出/导入，在客户端恢复权威 checkpoint 后重放未确认输入。当前世界很小，完整预测成本可控。
- 低成本过渡：仅对本地角色做无碰撞的视觉位移预测，规则位置仍来自服务器。这更快，但靠近树木、其他角色和投递区时校正会更明显。

无论哪种方案，音效、计分、抓捕、拾取和胜负都不能由预测直接提交；预测只改善表现，权威事件才能确认结果。

## 7. 地图、版本与确定性

### 7.1 地图真源

本地模式继续允许 `MapStorage` 从浏览器读取当前地图。在线房间改为：

1. 服务端从 `MapCatalog` 选择一张已发布且通过 `validateOrchardMap()` 的地图。
2. 生成稳定内容 hash，并把 `mapId`、地图版本、hash 和必要的完整地图数据放入房间握手。
3. 客户端验证 hash 后渲染同一份地图；本地 `localStorage` 不能覆盖在线房间地图。
4. 服务端用同一份地图实例创建 `GameSimulation`。

自定义地图以后可以增加为“上传 JSON -> 服务端解析/迁移/校验 -> 限额 -> 内容 hash -> 临时目录”的独立功能，不应把浏览器本地地图直接当房间权威。

### 7.2 构建与协议兼容

- 每次部署生成 `buildVersion`，协议另有整数 `protocolVersion`。
- MVP 只允许完全相同的 `buildVersion` 入局，避免地图、规则常量或事件类型不一致。
- 房间创建后锁定版本；服务器滚动发布时，旧房间应有完成当前局的宽限期，或明确提示维护中止。
- 输入重放文件记录 `buildVersion + protocolVersion + mapHash + seed + ordered input frames`。

### 7.3 确定性验证

在真正接网络前先增加一个 Node 规则测试：同一地图、种子和输入带运行两次，逐 tick 比较规范化 checkpoint hash。再用同一输入带分别在 Node 和浏览器运行，观察是否存在漂移。

服务端权威允许客户端预测偶尔漂移并校正，因此不需要为了跨运行时做到数学上的永久 bit-perfect 锁步；但重放一致性仍然会显著提升故障复现能力。

## 8. 断线、重连与失败策略

建议首版规则如下：

- 浏览器 `blur` 仍立即清空本地 held input，并发送中立输入。
- 服务端超过 250 ms 没收到某角色新输入，也强制中立，形成第二道防卡键保护。
- 意外断线后，房间暂停权威 tick，其他客户端显示“等待玩家重连 15 秒”。
- 服务端用不可猜测的 `rejoinToken` 识别原玩家；房间码只用于加入，不用于夺回座位。
- 15 秒内重连成功：发送完整房间状态和快照，双方准备后继续倒计时 3 秒再恢复。
- 超时：本局标记 `Abandoned` 并回到大厅。首版不记胜负，也不自动用 bot 接管。
- 玩家主动退出：不进入重连等待，直接标记放弃。

暂停策略比“断线角色原地不动但比赛继续”更适合当前 2 人非对称玩法，否则任一方的短暂网络波动都可能直接决定胜负。后续若加入公开匹配和排名，再设计限次暂停、判负和 bot 接管。

## 9. 安全与滥用边界

即使没有账号，演示版也保留最小输入信任边界：

- 本地与受信任局域网使用 HTTP/WebSocket；不提供 SSL/TLS。若以后公开部署，必须另行补 HTTPS/WSS、Origin 白名单和反向代理配置。
- 房间码使用加密安全随机数，并限制创建、加入、猜码和输入消息速率。
- 每条消息做运行时结构校验、长度限制和有限数值检查；异常频率持续超限时断开连接。
- 服务端只接受输入意图，不接受位置、地图替换、冷却完成、分数、事件或胜负声明。
- 昵称限制长度与字符，DOM 中用文本方式渲染。
- 不在 URL、日志或分析事件中记录 `rejoinToken`。
- 每房间限制玩家数、空房存活时间和最大比赛时长；房间销毁时清理 timer、输入队列和 token。

本项目首版无需“高级反作弊”。只要规则权威、角色所有权、消息校验和速率限制正确，已经消除了最直接的客户端篡改面。

## 10. 部署与扩容

### 10.1 MVP 部署

- Vite 静态资源可以由现有静态站点或同一个 Node 服务提供。
- Socket.IO 服务运行在支持长连接的 Node 进程中；本演示直接监听 `0.0.0.0:5190`，由 Vite 同源代理 `/socket.io`。
- 本地开发由 Vite 把 `/socket.io` 代理到独立端口，保持浏览器同源体验。
- 首版单实例、内存房间即可；进程重启会结束进行中的房间，这是可接受且应在 UI 中明确提示的 MVP 限制。
- 提供 `/healthz`、活动房间数、玩家数、tick lag、消息速率、快照字节数、RTT 和重连次数指标。

### 10.2 何时再扩容

单实例达到 CPU 或连接预算后，不能只加 Redis 广播就认为房间已水平扩展。每个权威 `GameSimulation` 必须始终只由一个 worker 推进，扩容需要：

- 入口按 `roomId` 做粘性路由或通过匹配服务把玩家送到房间所属 worker。
- Redis/数据库只存房间目录、短期会话和指标，不让多个 worker 同时 step 同一房间。
- 若届时公开匹配、跨进程房间生命周期和观战已成核心需求，再对比迁移 Colyseus 与继续维护自研 RoomManager 的成本。

## 11. 分阶段实施建议与退出条件

### Phase 0：无网络的服务端可运行性验证（已完成）

工作：让 Node 直接创建地图和 `GameSimulation`，运行命令带与 checkpoint/hash 测试；定义协议版本和座位所有权。  
退出条件：Node 构建通过；同输入重放稳定；没有浏览器 API 从共享规则依赖链泄漏进来。

### Phase 1：本机双标签权威竖切（已完成）

工作：Socket.IO 单房间、两个客户端、2 人座位、准备/倒计时、30 Hz 输入、20 Hz 全量快照、权威胜负；先不预测。  
退出条件：两个浏览器始终显示同一 tick/比分/胜负；非法角色输入被拒绝；本地模式测试不退化。

### Phase 2：玩家可用的同步表现（未实施）

工作：远端插值、本地预测/校正、事件去重、RTT 与修正量诊断、人工延迟/抖动测试。  
退出条件：在 30/80/120 ms RTT 场景下可完成整局；没有重复音效和重复计分；位置修正不造成明显瞬移。

### Phase 3：房间产品闭环（演示范围已完成）

工作：创建/加入房间码、座位 UI、准备、断线暂停、15 秒重连、主动退出、再来一局、错误提示。  
退出条件：刷新页面可用 token 回到原座位；重连失败会全量重同步；房间销毁无残留 timer/监听器。

### Phase 4：公网部署与观测（不在纯演示范围）

工作：WSS、Origin/限流、健康检查、单实例部署、负载与长时间 soak 测试。本期仅实现 `/healthz` 和内存房间诊断，不配置 WSS。  
退出条件：三客户端连续多局无状态分叉；服务端 tick lag、内存、消息量和异常断开有可读指标；发布/重启失败路径有明确 UI。

不要把四个阶段一次性合并成“大联机改造”。Phase 1 就足以回答最重要的问题：现有规则层能否稳定跑在服务端，以及两端是否能围绕同一权威状态完成一局。

## 12. 测试矩阵与首版质量门槛

### 12.1 自动化

- 纯规则：相同输入带/种子/地图重放一致；非法数值不会进入模拟。
- 协议：跨版本、错误 match、未授权角色、重复 seq、旧 seq、超大消息和快速刷包。
- 多浏览器：两个 Playwright context 创建/加入同房间，各自用真实键盘控制所属角色。
- 收敛：每个权威快照后，各客户端最终 `matchState`、比分、苹果状态一致。
- 事件：同一 `eventId` 即使重复到达，音频/VFX 只触发一次。
- 网络：延迟、抖动、短断线、刷新、超时离开、服务端关闭。
- 生命周期：连续再来一局不会保留苹果、冷却、输入、事件或上一局的 `matchId`。

### 12.2 建议观测门槛

- 服务端权威 tick 不长期落后，补 tick 上限触发必须有日志与指标。
- 稳态每客户端下行流量先以 50 KiB/s 为预算，实际测量后再决定是否做字段裁剪、delta 或二进制编码。
- 远端插值不出现倒退 tick；本地校正距离记录 p50/p95/max。
- 15 秒内重连成功后不丢座位、不重复事件、不改变已确认比分。
- 进行中的所有胜负只能由服务端 `GameSimulation` 产生。

当前状态很小，首版优先使用可读的完整快照。只有测量表明带宽或序列化是瓶颈时，才引入 delta、MsgPack 或紧凑二进制；过早压缩会让联机排障更困难。

## 13. 游戏设计约束

### 13.1 简版设计契约

- 玩家承诺：在一场短促、非对称的果园追逐中，一方通过协作封路和飞扑抓捕，另一方冒险搬运苹果并选择负重与安全的平衡。
- 目标感受：紧张、清晰、可复盘；网络延迟不能让命中像随机判定。
- 主要动词：守卫移动/飞扑，kid 移动/拾取/丢弃/投递。
- 核心循环：接近目标、判断对手路线、使用角色动作、根据抓捕或苹果进度重新选择路线。
- 失败/重试：三次抓捕或全部苹果送达后快速结算；联机“再来一局”由双方准备确认。
- 技巧表达：守卫协作夹击与飞扑时机；kid 的路线、拾取时机、负重管理和诱导。
- 可读性承诺：输入即时反馈，远端运动连续，所有计分和命中由明确权威事件表现。
- 非目标：联机首版不借机改变地图、胜负数值、角色速度或碰撞规则。

核心循环契约：玩家通过移动与角色动作争夺苹果进度或抓捕次数，同时对手路线、负重和技能冷却制造风险；成功推进阵营胜利条件，失败则失去位置、苹果或一次抓捕机会，并可快速进入下一轮决策。

### 13.2 场地与节奏约束

联机首版使用与本地模式相同的已发布地图和固定镜头，不做网络专用关卡。需要额外试玩确认：

- 2 人模式中一位玩家同时操控两名守卫时，远程输入与键位仍然可理解。
- 3 人拆分守卫后，协作收益是否过高，是否需要调整守卫速度或抓捕目标。
- 100 ms 左右的远端插值是否会让飞扑预警和 kid 的无敌窗口难以判断。
- 服务端命中位置与客户端视觉位置有误差时，命中特效是否能解释校正，而不是像“隔空抓到”。

这些是联机手感风险，不应通过客户端自行放宽碰撞来掩盖；必要时只在服务端统一调整碰撞宽限或动作前摇，并同时回归本地规则。

## 14. 已确认的五个决定

| 决定 | 推荐默认值 | 若选择另一方向的影响 |
| --- | --- | --- |
| D1 首发人数 | 2 个客户端：kid vs 一人双守卫；协议兼容 3 人 | 首发 3 人需要重新试玩平衡、缺人和掉线策略 |
| D2 网络框架 | Node.js + Socket.IO，自定义权威房间 | Colyseus 会增加 Schema/配置迁移，但房间平台能力更完整 |
| D3 断线规则 | 立即暂停，保留 15 秒，超时本局作废 | 继续比赛或判负更竞技，但网络波动惩罚更大 |
| D4 地图范围 | 仅服务端发布地图 | 自定义地图需要上传、校验、限额、hash 和安全边界 |
| D5 身份与入口 | 匿名房间码 + 私有 rejoin token | 账号/公开匹配会引入数据库、认证、隐私和运营需求 |

本期按以上默认值完成 Phase 0 + Phase 1，并一并完成演示所需的创建/加入房间、准备、断线暂停、15 秒原席位重连、退出和再来一局。是否投入 Phase 2 的预测与插值，留待实际跨设备试玩后决定；公网部署不在本项目范围。

## 15. 实施结果

### 15.1 入口与运行方式

- `/`：保留原有同键盘单机模式和浏览器本地地图。
- `/online.html`：2 个桌面浏览器客户端，`guards` 席位拥有两名守卫，`kid` 席位拥有小孩。
- `npm run dev`：同时启动 Vite `127.0.0.1:5188` 与房间服务 `0.0.0.0:5190`。
- `npm run preview`：同时启动构建预览 `127.0.0.1:4188` 与同一房间服务。
- `/healthz`：房间服务健康状态与内存房间诊断。

### 15.2 已实现边界

- `GameDriver` 把本地模拟和在线权威快照接入同一套 Three.js、HUD 与音频表现层。
- 服务端每房间持有一个 `GameSimulation`，60 tick/s 固定步长推进，20 Hz 广播全量状态；客户端以 30 Hz 发送变化、动作边沿和心跳输入。
- 服务端校验协议/构建版本、有限数值、移动归一化、输入序号和角色所有权；客户端不能提交位置、计分、命中或胜负。
- 在线房间固定使用服务端发布的 Sweet Orchard Island 地图与内容 hash，不读取客户端 `localStorage` 地图。
- 意外断线立即暂停；15 秒内使用私有 token 恢复原座位和权威快照。主动离开不进入等待。
- 本期没有客户端预测、远端插值、账号、公开匹配、持久化或多实例扩容；Node 进程重启会丢失内存房间。

### 15.3 验证记录

- `npm run build`：严格 TypeScript 与 Vite 生产构建通过。
- `npm test`：58 项通过，50 项按项目/视口条件跳过；包含既有单机规则、真实键盘、编辑器、视觉检查以及新增双标签联机和断线重连。
- `npm run preview`：`/online.html` 返回 200，房间服务 `/healthz` 返回健康状态；预览入口和无 SSL 服务可同时启动。
- `npm audit --json`：生产与开发依赖均无已知漏洞。
- `npm run inspect:canvas`：画布非空、无控制台或页面错误；163 draw calls、100,840 triangles、130 geometries、14 textures，均在当前桌面预算内。
- `tests/server-simulation.spec.ts`：同地图、种子和命令带在 Node 运行两次得到一致结果；非法 `NaN` 输入被拒绝，超范围移动被规范化。
- `tests/multiplayer.spec.ts`：验证权威移动收敛、未拥有角色输入被拒绝、短断线暂停与同席位恢复。
- 联机大厅与权威对局截图已人工检查：席位、准备、房间码、网络状态和 HUD 在 1280 × 720 桌面视口无明显遮挡。

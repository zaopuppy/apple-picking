## 方向重审：明亮分层果园岛

### 参考图中真正要学习的内容

参考图的价值不是某一棵树或某一栋房屋，而是下面八个能落实到 Three.js 的构图规则：

1. **先有完整岛屿剪影，再有内部摆件。** 海水形成稳定负空间，草地不是铺满视口的无限矩形。
2. **水平顶面与垂直崖面同时可见。** 草地顶面、泥土崖壁和水面至少形成三个明确高度带，即使角色暂时只在一个高度行动。
3. **方格只作为秩序感，不作为满屏调试网格。** 顶面可有轻微草地格纹，但区域边界由海岸、台地、广场和植被决定。
4. **道路是宽阔的场所与连接面。** 沙地广场、院落和短连接比细长、等宽、横贯全图的管线路网更重要。
5. **水体参与构图。** 海岸、池塘、短水道、桥梁和瀑布共同提供方向标；水不能只是一个贴在草地上的蓝色椭圆。
6. **地图由几块可命名区域组成。** 中央广场、果园、住宅/投递区、池塘花园、木材/海滩区各有自己的轮廓和道具组合。
7. **密度有梯度。** 边缘和地标周围较密，玩家追逐和转向的中心区域较空；不是全图均匀撒树、树桩和苹果。
8. **高明度、低写实度、柔和接触感。** 高饱和草绿与青蓝水面配暖沙色/土色，几何轮廓圆润，阴影负责落地而不是制造戏剧性黑区。

这套方向应被描述为“明亮、玩具感、分层果园岛”，而不是在代码和资产命名中直接使用某个商业游戏的品牌风格。

### 当前画面为什么失败

当前默认桌面截图 `artifacts/canvas-inspection/desktop.png` 与代码结构共同暴露了以下问题：

- `createTilePlacements` 用 336 个方格地块覆盖整个矩形视口，画面的第一阅读层是棋盘，不是岛屿。
- `createGeneratedPaths` 先放一横一竖的跨场道路，自动铺路得到的是细长管线；它提供连通性，却没有产生广场、庭院或可停留的场所。
- 地表选择只有 `forest / sand / rock / water`，没有海岸轮廓、草地压边、崖面、台地层级、瀑布和桥面等组合语义。
- 当前 `worldStyle` 只记录 KayKit 主题与方格/六边形，无法表达色板、岛屿外形、高度层、区域密度和水岸规则。
- 建筑、人物、苹果和树木相对整张 72 × 54 地图过小，大片空地只有相同地砖，局部资产再精致也会像散落的棋子。
- 现有完整 KayKit 目录是素材库，不是美术指导；把更多模型随机放入场景只会提高杂乱度。
- 场景背景是单色，地形一直延伸到画面边缘，缺少参考图中最重要的海水负空间和岛屿边缘。

当前性能不是主要矛盾。最近一次桌面诊断为 90 draw calls、71,203 triangles、129 geometries、12 textures，全部低于现有桌面起始预算；画面问题主要是构图、比例、层次与资产选择。

### 推荐的标准地图：Sweet Orchard Island

第一张地图必须手工构图，用来锁定尺度、色板、模块和玩法节奏。它不是参考图的复刻，而是为“偷苹果并送达”设计的原创岛屿。

```text
                         北 / 画面远侧
        ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
        ~  [A 高台果园] -- 小桥 -- [B 住宅与投递院]  ~
        ~       |                    |             ~
        ~  安全外环路          高风险短路线         ~
        ~       |                    |             ~
        ~ [C 木材海滩] -- [D 中央节庆广场] -- [E 池塘花园] ~
        ~       |          kid 起点          |      ~
        ~       +--------- 南侧恢复带 --------+      ~
        ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
                         南 / 画面近侧
```

区域职责：

| 区域 | 视觉角色 | 玩法角色 |
| --- | --- | --- |
| A 高台果园 | 成排果树、暖色土壤、后景台地和小瀑布 | 苹果密集但出口较少，拾取效率高、被包夹风险高 |
| B 住宅与投递院 | 一栋主屋、围栏、邮箱/篮筐、短沙路 | 投递目标明确；从中央走最短，从外环走最安全 |
| C 木材海滩 | 沙地、码头、木材堆、棕榈或灌木 | 低密度恢复区和绕开守卫的长路线 |
| D 中央节庆广场 | 最大连续沙地、树池/喷泉式小地标 | 三向决策中心，也是最容易发生追逐交叉的高风险区 |
| E 池塘花园 | 池塘、花圃、矮篱笆、短桥 | 环形走位与视线切换，提供第二类苹果获取区 |

路线合同：

- 从任一苹果密集区到投递区至少有一条短而暴露的路线和一条长而安全的路线。
- 中央广场至少有三个出口，不成为单一瓶颈。
- 高障碍只放在远侧、边缘或地标内部；中央与南侧恢复带保持低矮。
- 桥宽首版至少容纳两名角色错身；桥不能成为唯一通往所有苹果的通道。
- 六个苹果分成 3 组，每组 2 个，避免现在全图均匀撒点造成目标感缺失。

核心循环合同不变：玩家在果园/花园拾取苹果，在守卫追逐压力下选择短路线或安全外环送往住宅院；成功增加投递数，失手会掉落或失去已送达苹果，重开保持快速。

### 高度策略：先做 1 + 1 层，不立刻重写玩法

推荐第一版使用“单层可玩面 + 一层视觉台地”：

- 角色、苹果、守卫和桥面仍在同一规则高度，由现有 XZ 模拟负责。
- 海水位于主可玩面以下约 `1.2–1.6` 单位，岛岸显示土色崖壁和草地压边。
- 远侧果园或住宅后方可增加一层不可进入的景观台地，高约 `1.4–1.8` 单位，用围栏、崖边和植被明确阻挡。
- 瀑布只连接视觉台地与海/池塘，不提供角色上下通道。
- 等第一张地图的构图和路线通过后，再决定是否让楼梯/坡道进入玩法；真正多层导航需要升级碰撞、路径验证、角色 Y 状态与相机遮挡，不应夹带在第一轮美术实现中。

这能获得岛岸、崖面、瀑布和桥梁的空间感，同时把风险控制在渲染与关卡布局层。

### 地形与材质语言

推荐以共享材质角色统一现有资产，而不是沿用素材包各自的默认颜色：

| 材质角色 | 建议色域与表面 | 用途 |
| --- | --- | --- |
| `islandGrass` | 明亮中绿，粗糙度高，极轻微顶面色差 | 主草地与台地顶面 |
| `grassEdge` | 比主草地略亮的窄边 | 海岸与崖顶压边，强化玩具切片感 |
| `cliffSoil` | 暖棕/黄褐，分层条带或低频色差 | 岛岸、台地和瀑布两侧崖壁 |
| `pathSand` | 低饱和暖米黄，边缘略软 | 广场、院落、短连接和海滩 |
| `waterShallow / waterDeep` | 青绿到天蓝的双层色带 | 海面、池塘与水道；深浅表达边界 |
| `waterFoam` | 偏青白，不透明度克制 | 海岸、瀑布落点和桥墩附近 |
| `woodWarm` | 中明度暖木色 | 桥、围栏、码头和房屋细节 |
| `objectiveGold / appleRed` | 少量高对比暖色 | 投递区、苹果和关键交互，不扩散到背景 |

具体表现：

- 地表网格只保留非常轻的 4 × 4 米节奏线或色块变化，不能再出现当前高对比满屏边线。
- 海岸与台地使用模块化边、内角、外角和端点；顶面、草边、崖面分开共享 geometry/material，便于实例化。
- 水面优先使用低成本双层滚动法线/顶点扰动和岸边泡沫带；不使用重 Bloom，不用效果掩盖空场景。
- 树冠、灌木和岩石使用 2–4 个轮廓变体，通过尺度与旋转形成簇；重复小物件实例化。
- 主光保持一个暖色方向光，环境填充略偏天蓝；软阴影与廉价接触阴影只负责把角色、树与建筑压在地面上。

### 相机与构图

当前 34° 斜俯角不是唯一问题，真正缺少的是可见崖面和水边。建议先做两个同机位候选：

1. **正交镜头，推荐基线**：保持玩具地图的稳定比例，把地面法线夹角调到约 `38–42°`，让崖面可见；岛屿四周保留约 8%–15% 的海水画面。
2. **弱透视镜头，A/B 候选**：小 FOV（约 `20–25°`）与较远机位，增加远近层次但不让近侧角色明显变形。

无论选择哪种，标准桌面画面中主岛不能贴满四边，玩家视觉高度目标约为画布高度的 3%–4%，中央广场、最近苹果组和投递方向应同时可读。窄屏使用独立构图，不通过简单裁掉左右海岸来适配。

## 第一轮：可玩视觉试验场

入口统一使用主游戏，不做只能旋转观看的静态展台。KayKit 村庄已经成为默认入口，避免只有知道查询参数的人才能看到：

- `pond` 地标：六边形水面只铺在不可进入椭圆内，岸边用过渡地块和岩石提示。
- 树木：继续使用已有树碰撞和自然包模型，下一轮根据选定风格决定是否统一为 KayKit 森林。
- 边界城墙：只放在现有竞技场夹紧边界上，不在内部制造“看似阻挡但可穿过”的墙。
- KayKit 世界加载失败：保留现有程序化地面、路径、围栏和地标作为完整回退。

### 当前优先级

- 第一优先级是可玩性：目标可达、竞技区域开阔、至少存在多条有效接近路线、不可进入区域有可信碰撞。
- 第二优先级是世界辨识度：村落、河畔和城堡应当只看画面轮廓就能区分，而不是换几块地表颜色。
- 226 个模型全部保留为可用素材库；生成器根据地表邻接、建筑槽位和地图主题选择子集。
- 本阶段不以移动端资源请求、draw calls、三角面和包体预算限制地图设计；自动诊断继续记录数据，但不作为候选淘汰条件。
- 性能优化移到世界方向和编辑器工作流稳定之后，再做实例化、LOD、按需加载和移动端降级。

## 地图 v5 预留：多个投递区

P1.2 已先完成规则验证，但没有强制升级存档版本：当前 v4 兼容桥同时保留单个主字段：

```ts
deliveryZone: Vec2
```

以及可选的多点字段：

```ts
deliveryZones?: Array<{ id: string; x: number; z: number }>
```

没有 `deliveryZones` 的旧地图自动按一个主投递点运行。方向通过试玩后，v5 再把列表改为必填，并允许每个点拥有独立半径：

```ts
deliveryZones: Array<{
  id: string;
  x: number;
  z: number;
  radius: number;
}>
```

拟定规则如下：

- 所有投递区等价；进入任意一个都可投递。
- 投递区重叠时先选最近中心，再按 `id` 稳定排序。
- 苹果位于任意投递区内都保持“已送达”；离开所有投递区才失去该分。
- 事件携带 `zoneId`，便于 HUD、音效和统计定位。
- v4 单投递区在解析时自动视为含一个元素的数组，不需要立即重写本地存档。
- 数量由地图尺寸和预设推导，不写死为固定数量；当前标准岛使用 4 个点验证上限，旧地图仍使用 1 个。

## 编辑器方向（第三、四轮）

编辑器最终保存语义而不是具体 GLB 文件名：森林、道路、沙地、岩地、水域、院落、建筑槽位和投递区。渲染层负责把语义自动拼成 KayKit 地块，避免用户逐格挑选 `roadA` 到 `roadM`。

需要的编辑能力：

- 地表语义画笔与道路/岸边自动拼接。
- 建筑/院落的占地预览、碰撞范围和比例参考人形。
- 多投递区的添加、移动、半径调节和删除。
- 2D 快速编辑与 3D 即时预览切换。
- 随机候选继续保留，但生成“区域骨架 → 地标 → 宽通路 → 装饰”，不再用树桩填满剩余空间。

### 当前可用的人工搭建流程

1. 打开 `/editor.html`，在“KayKit 世界样式”中选择林间村落、河畔集市或城堡果园。
2. 地块形状默认选择“方形地块”；需要比较旧效果时可切换为六边形。
3. 选择“铺设宽路”后拖动绘制道路骨架。方格地图会把输入吸附为水平/垂直折线，渲染层再根据四邻接自动选择 KayKit A–E 直路、转角、T 口和十字路口。
4. 选择“KayKit 建筑”，再选择具体模型与 0° / 90° / 180° / 270° 朝向，点击画布放置。编辑器不会保存任意斜角建筑。
5. 用池塘、果园地块、草地空场、树木和出生/目标工具补齐规则内容；保存前继续执行可达性校验。
6. 在画布上方切换“3D 预览”，用左键拖动旋转、滚轮缩放、右键平移；切回“2D 编辑”后继续放置。
7. 点击“使用并游玩”，进入 `/?world=custom` 检查真实碰撞、镜头遮挡和完整游戏循环；左上角“编辑”可返回继续调整。

当前 3D 视图是同步的视觉检查器，放置、拖动和删除仍在 2D 视图完成。这是有意的范围边界：先让构图判断可靠，再决定是否值得开发完整的 3D 拖拽工具。
